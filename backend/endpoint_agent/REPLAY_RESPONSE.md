# Visual replay, live desktop and endpoint response

## Investigator features

**Session replay** stores up to 600 sequence-numbered screens per session. It supports previous/next navigation across pages, current field values, added/changed/removed field highlighting, original JPEG display, and original supplied HTML in an isolated iframe. The iframe disables scripts, forms, same-origin access and external resources. Display markup also removes navigation/refresh instructions, event handlers and embedded frames, and disables form controls; the retained source remains unchanged. Original HTML is retained but interactive JavaScript behavior and external assets are not replayed. If original pixels/HTML were not captured, reconstructed text is shown with its limitation rather than presented as an original screenshot.

Recorded sessions can be tagged mainframe, web or client-server. Existing decoded network search records can replay their capture session in decoder order grouped by direction. Their original per-screen times/pixels are unavailable and gaps remain in the source capture. TLS/SSH ciphertext cannot reconstruct a screen without an authorized decoded source. The API accepts historical timezone-aware timestamps; the manual screen form uses the current time. Frames containing text/fields are indexed automatically, while image-only frames require separate OCR to become searchable.

**Search content** searches all indexed platforms with optional platform, source and timeframe filters. Results share relevance ranking and pagination across sources. **Replay result** opens the exact linked frame in its recorded session. Existing parsed records without a recording open a clearly labelled source display. Network session results open the decoded neighbouring records. Live viewing uses a continuously updated HTTP JPEG stream (one capture per second, UI polling every two seconds), rather than an RDP protocol connection. Recorded screens remain available after a session ends.

## Endpoint response and audit

Only administrators queue response commands. Every command has the authenticated actor, required reason, expiry, dispatch lease and acknowledged result. Agent requests authenticate with their endpoint token. Duplicate results are idempotent; changed acknowledgements are rejected. The agent persistently claims a command before execution; a restart during an action produces an indeterminate result instead of repeating a potentially destructive action. Re-registration of an existing machine requires its current token; unauthenticated callers cannot rotate another agent's identity.

The **Endpoint response** panel lists process results, confirmed termination, isolation/release/status, file and Windows restore points, live viewing/control and an audit history. Queued/dispatched actions are not displayed as completed. Control text is redacted from operator/audit responses and cleared after acknowledgement or expiry. Audit records capture operator actions and agent outcomes; they are application records, not a cryptographically tamper-proof external log. Database access must be controlled by the deployment.

Process listing is bounded to 500 entries and records creation time. Termination checks PID plus creation time, protects the agent/parent and named Windows system processes, sends termination once and waits up to five seconds. A timeout is reported as unconfirmed; no automatic force-kill occurs. OS permissions can reject access.

## Local opt-in and deployment

Copy `example-response.json` into the deployed agent configuration and replace the server/token/paths. Response is off by default. Enable `response.enabled` and only approved `allowed_actions`. Install `requirements-response.txt` in the agent's runtime for psutil, Pillow and PyAutoGUI. Tkinter must be available for local desktop consent. The normal endpoint worker polls response commands and supplies recordings. The server also requires Pillow for JPEG validation. Use authenticated HTTPS for an off-host deployment.

Set `desktop_enabled` for viewing and `control_enabled` for input. A visible local prompt identifies the requesting operator and recording duration. If the prompt cannot be displayed or the user declines, the session fails. An always-on-top Stop button remains visible during the session. The session expires after at most ten minutes, and recording/transport failure ends local control. Only the owning operator can send input. Primary-display clicks use normalized coordinates; supported special keys, printable ASCII typing and bounded scrolling are available. PyAutoGUI's corner fail-safe remains enabled. Services in Windows Session 0 cannot capture/control an interactive user's desktop: run this component in that user's session. Secure desktop/UAC, other displays, full-motion video and reconnecting a session after agent restart are outside this adapter's scope. Closing the browser view does not extend the endpoint's fixed expiry; use Stop desktop session to end immediately.

## Windows network isolation

The Windows firewall adapter adds two named host-firewall block rules covering IPv4/IPv6 addresses except explicitly configured management IPs. It preserves existing firewall profile defaults, requires profiles already enabled and verifies active rules. Explicit block rules take precedence over unrelated allow rules for other destinations. Isolation remains in place across agent restarts until release removes the adapter's rule group. This is host firewall isolation with management exceptions, not a switch/VLAN quarantine or proof against privileged malware altering the firewall.

Configure every resolved management-server IP in `management_addresses`; the agent checks this before isolation. If the server URL needs DNS, explicitly include the deployed DNS resolver addresses too. Those exceptions permit traffic to the listed IPs and are not restricted to only a management port; choose dedicated, trusted endpoints. An existing blocking policy may still prevent management traffic. Group Policy, third-party filters, VPNs and local loopback behavior need target-machine validation. Local recovery can remove only the `ZANAQ Endpoint Isolation` rule group with administrator tools if connectivity is lost. No firewall operations are run by automated tests.

## Rollback scopes and verification

**File rollback points** capture up to 1,000 files / 50 MB from 1–10 explicit folders plus host/system metadata. Roots cannot be whole drives or overlap the snapshot store. Links/junctions are rejected. Manifests and content hashes are checked before restoring. Rollback creates a backup point, overwrites only captured files atomically per file, and verifies their hashes. Newly created files, permissions, registry values, databases requiring transaction-consistent snapshots and uncaptured OS state are not rolled back. A mid-restore failure can leave some files restored; the backup point permits recovery. Storage is capped at 20 points per agent; archive approved points before adding more. The local point registry and files must stay together.

**Windows system restore points** use Windows client System Restore when `windows_restore_enabled` is explicitly enabled. This requires administrator privileges and existing System Protection. Creation is verified by finding the uniquely labelled native point; Windows' daily point limit can reject creation. These points protect Windows-managed system files/settings, not personal files or a full disk image. Restoring a native point schedules an endpoint restart in 30 seconds. The command is recorded as **pending verification**. Reconnect after reboot, then use Verify after restart to inspect Windows' restore status. Verification requires a new boot and Windows' successful last-restore result; it cannot prove the last result belongs to exactly that point or compare every OS file. A failed/unknown result remains visible. System Restore can affect installed software and the agent itself; test recovery and preserve management configuration/state. This implementation does not change System Protection settings, bypass point-frequency limits, or run actual restores during tests.

## APIs and limits

Authenticated replay APIs are `/api/replay/sessions`, `/sessions/{id}/frames` (forward `after` or backward `before` sequence cursors), and `/api/replay/from-search/{document_id}`. Writers may import recorded sessions/frames. Assigned agents submit bounded JPEG frames through `/api/replay/agent/sessions/{id}/frames`. Frames are at most 512 KB with bounded dimensions; recording caps stop further ingress. Original JPEG storage has a global 512 MB ingress cap. There is no automatic recording deletion; archive recordings and configure database/text-index retention before sustained deployments.

Administrator commands: `POST /api/response/agents/{id}/commands` with `action`, typed `arguments` and `reason`. Authenticated readers can retrieve `/commands` and `/audit` for an agent. Agents use `GET /api/response/poll`, `POST /api/response/commands/{id}/result`, and `/api/response/session-ended`. There is no arbitrary shell or unrestricted file-path execution API. Commands expire after ten minutes; input expires after ten seconds and is not replayed on a delivery lease timeout.

Validation covers role and token boundaries, ordered replay/paging, field comparison, search links, HTML parsing, image bounds, durable receipts, expiry, PID reuse, interrupted action journals, local desktop consent/stop, hash-verified file restore/backup and mocked Windows firewall/System Restore contracts. Physical Windows firewall, consent desktop and native restore/reboot behavior still require an approved test machine.
